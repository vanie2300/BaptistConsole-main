Process model

  • Main process (main.js) creates the console window, intercepts popups via setWindowOpenHandler, and guards presenter windows (Esc-to-close, minimize/hide-to-close). Presenter windows are placed automatically on the configured display.
  • Renderer iframes — Bible and Hymn tabs are <iframe>s inside index.html to keep the modules isolated from each other.
  • presenterApi — exposed through preload.js + presenter-proxy.js so the iframes can call IPC (display pickers, hymn file I/O) without touching the filesystem directly.

Settings flow

  1. Settings are stored in localStorage under the keys defined in shell.js (KEYS map).
  2. On Apply, pushBibleSettings() / pushHymnSettings() post a *SettingsUpdate message to the relevant iframes.
  3. Each module applies the setting locally and forwards the update to its presenter window via postMessage.
  4. settingsUpdate also carries shared presenter colors, fonts, and per-module background images.

Search

  • Bible — keyword search builds a flattened index of the current scope and returns matching references with highlighted text (appendHighlightedText).
  • Hymns — title substring filter with case-insensitive match highlighting sent to the rendered list (highlightMatch).

Auto-fit

  • Bible — projected text is fit against the viewport: fitPresenterText computes size from available space, min/max font bounds, and a display bias. Reference size scales independently via an inline calc (calc(clamp(0.9rem, 1.8vw, 1.6rem) × n/100)).
  • Hymns — slideToHtml uses fixed base sizes per preview mode; fitFrameText shrinks smoothly only when overflowing, keeping a readable floor. Titles use fitCurrentTitle with a 4vw minimum and safe center alignment so overflow scrolls instead of clipping.

Background images

Per-module keys (settings_bibleBgImage, settings_hymnBgImage) replace the legacy shared settings_presenterBgImage. On first run the legacy key is migrated to the active module's key and then removed, so backgrounds no longer leak between modules.

IPC channels

All IPC is declared in main.js and surfaced through preload.js. The renderer never touches the filesystem directly.

The preload bridge

preload.js runs with contextIsolation: true and nodeIntegration: false. It exposes two globals:

  • window.windowControls — minimize(), maximize(), close() for the custom title bar.
  • window.presenterApi — getDisplays(), setPresenterDisplay(id), getHymns(), saveHymns(hymns), pickBackgroundImage(), closeWindow().

The iframe presenter proxy

The Bible and Hymn tabs are <iframe>s, so they cannot see window.presenterApi directly. presenter-proxy.js (injected into each iframe) bridges the gap:

  1. The iframe calls presenterApi from the proxy.
  2. The proxy posts { type: 'presenterApiRequest', requestId, method, args } to parent.
  3. shell.js resolves the method and replies { type: 'presenterApiResponse', requestId, result, error }.
  4. Pending calls time out after 5 seconds.

The proxy exposes getDisplays, setPresenterDisplay, getHymns, and saveHymns — file-picker and window-close remain main-frame only.

Inter-frame messages

All cross-window communication uses postMessage with a string type. The console → iframe → presenter-window chain keeps modules isolated.

Multi-screen presenters: the module's Display picker is a modern dropdown (shared component display-picker.js / display-picker.css) listing each screen by name or size (primary first with a badge). A row acts like a checkbox; Auto clears the explicit choice, All Displays selects every screen. Updates — verseUpdate, navigate, and settings messages — are broadcast to every open projector. Each window's name carries its display id (bible-presenter-d<id> / HymnPresentation-d<id>); main.js reads it from details.frameName in did-create-window to place the window, falling back to the set-presenter-display id and then the primary display. Defaults: with one display detected, it is pre-selected; when more than one display is detected nothing is picked (no specific screen targeted). Display hot-plugs are pushed to the pickers (displays-changed broadcast + onDisplaysChanged) so new screens appear without a restart.

Presenter window lifecycle

main.js never opens presenters directly — they are popups produced by the module iframes. The flow:

  1. A module calls window.open (or the equivalent); setWindowOpenHandler permits only presentation.html and about:blank popups.
  2. did-create-window attaches the guard and places the window via setBounds on the configured display after load.
  3. Guards enforce behavior:
    • Esc inside a presenter destroys it.
    • Minimizing/hiding destroys it (watchdog checks every 500 ms).
    • Esc with the main window focused destroys all presenters.
  4. Presenters are normal windows (never always-on-top) so users can Alt+Tab freely.
